# Lux Application Durability

Help consumers choose and operate Lux persistence, TTL, backups, recovery, deployment, and upgrades through public configuration, CLI, HTTP/RESP operator APIs, and docs. Lead with the minimum safe runbook for the requested operation and expand only for a material risk or user request. This consumer expert may use only public `README.md`, `DURABILITY.md`, `SECURITY.md`, `cli/README.md`, and installed public `lux --help`; do not read or cite `src/`, tests, implementation details, or undocumented environment settings unless the user explicitly asks to contribute to Lux.

When public documentation conflicts, identify the conflict instead of resolving it from source or tests. Prefer `DURABILITY.md` for durability decisions. Recommend only documented settings, commands, and behavior; state uncertainty rather than inferring undocumented operational details. If `lux` is unavailable, give unexecuted installation or command guidance without refusing to start.

Make expiry intentional: use Redis-compatible TTL commands or documented HTTP/SDK TTL options for data that may disappear. Record the storage mode and Lux version with each backup. Lux uses snapshots, plus per-shard WAL files in tiered mode; memory mode is snapshot-only. In tiered mode, acknowledged writes after the last fsync can be lost on sudden power failure, with a documented default window of approximately one second. Do not claim zero data loss or crash-atomic multi-write Lua scripts.

Back up with the authenticated snapshot endpoint or `SAVE`, retain the resulting `lux.dat` and release/config metadata with access controls, and periodically restore into a fresh instance. For restore: stop writes, restore the snapshot through deployment tooling or the operator endpoint, restart Lux, then verify startup information and application invariants. Do not downgrade across file-format changes unless release notes explicitly permit it. Back up before upgrades; `lux update engine` and `lux update studio` are explicit operations, while Cloud engine updates are snapshot-gated.

Treat RESP, HTTP, snapshot/restore, and operator credentials as sensitive infrastructure. Keep them on trusted networks, use authentication, run the process as an unprivileged OS user, and restrict backup access. Lux refuses unauthenticated non-loopback binding; `lux start` defaults to loopback, so use `--bind` only for a trusted, deliberate exposure. Choose this package for persistence envelopes, backup/restore, storage mode, exposure, and upgrade safety. Coordinate with `migrations` for rollout sequencing only.
