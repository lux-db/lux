# Lux Application Push

Help consumers integrate Lux push through the public SDK, CLI, and management API. Lead with the minimal runnable consumer path for the requested platform and expand only for a material delivery risk or user request. Do not inspect or modify Lux engine internals unless the user explicitly asks to contribute to Lux itself. The repository documents the TypeScript SDK; for native iOS, Lux starts only after platform-native APNs token acquisition. Use that documented integration boundary and never invent a native Swift Lux SDK or method. Use `sdk/README.md`, installed public `@luxdb/sdk` types, `cli/README.md`, and `MANAGEMENT_API.md` as authority.

Before emitting runnable TypeScript, verify exact package paths, method signatures, and exported types in public SDK docs/types. Valid package paths are only `@luxdb/sdk`, `@luxdb/sdk/browser`, and `@luxdb/sdk/ssr`; never substitute ecosystem-memory names. Verify CLI syntax in public docs or installed `lux push --help` before emitting commands. If a CLI or package manager is absent, provide unexecuted install commands for `npm`, `pnpm`, `yarn`, or `bun` as appropriate, without requiring one to be present.

Configure delivery before registering devices. Use `lux push status --check` for local health or `lux push status my-app --check` for an explicit Cloud project. Initial local and Cloud APNs setup requires a key file: use `lux push apns set --team-id TEAM_ID --key-id KEY_ID --topic com.example.app --environment sandbox --p8-file AuthKey_KEY_ID.p8` locally, or `lux push apns set my-app --team-id TEAM_ID --key-id KEY_ID --topic com.example.app --environment production --p8-file AuthKey_KEY_ID.p8` for Cloud. Later metadata-only APNs updates may omit `--p8-file` to preserve the existing encrypted key. Use `lux push vapid enable --subject mailto:push@example.com` locally or `lux push vapid enable my-app --subject mailto:push@example.com` for Cloud; an omitted project is local and a positional project is Cloud. APNs credentials are read from the named file and provider secrets are not shown in status. Treat `lux push vapid rotate --subject mailto:push@example.com --yes` or `lux push vapid rotate my-app --subject mailto:push@example.com --yes`, `lux push vapid disable --yes` or `lux push vapid disable my-app --yes`, and `lux push apns clear --yes` or `lux push apns clear my-app --yes` as intentional invalidating actions that require client resubscription where applicable.

Use `lux.push.register(options)` from a signed-in client to register the current subject, or `lux.push.registerFor(subjectId, options)` only from trusted secret-key server code. Use `lux.push.unregister(id)`, `lux.push.unregisterByToken(token)`, and `lux.push.devices(subjectId?)` with their documented key boundaries. For Web Push use `lux.push.getVapidPublicKey()` or `lux.push.subscribeWebPush(options)` with an active service worker and user permission. Send with `lux.push.send(subjects, notification)` from trusted server code only; handle `{ data, error }`. Its `{ enqueued }` result confirms enqueue, not provider acceptance, device delivery, or end-user display.

For APNs, preserve the token environment (`sandbox` or `production`), use documented priorities, and do not send `data.aps`. Images need an iOS Notification Service Extension; action categories and critical alerts require the matching app registration or Apple entitlement. Choose `push` for provider setup, device registration, payloads, targeting, and delivery diagnosis. Coordinate with `auth` only for self-registration identity and with `durability` only for deployment/backup considerations.
